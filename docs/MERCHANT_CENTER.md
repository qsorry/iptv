# مزامنة Merchant Center والخلاصات

## لماذا API لا خلاصة مجدولة
الخلاصة تعمل بالسحب: جوجل يجلبها مرة يومياً، فيبقى سعر معدّل أو مخزون نافد خاطئاً حتى ٢٤ ساعة —
إعلانات على سعر غير صحيح، ثم تعليق المنتج أو الحساب. الـ Content API يدفع التغيير خلال دقيقة.

**لا تربط خلاصة مجدولة والـ API على نفس المنتجات**: تتنازعان على نفس `offerId` وتُكتب إحداهما فوق
الأخرى. التقسيم المعتمد هنا:

| القناة | المصدر |
| --- | --- |
| Google Merchant Center | Content API (هذا المستند) |
| كتالوجات Meta · TikTok · Snapchat | `GET /feed/products.xml` بسحب مجدول |

المصدر المحلي واحد (`listCatalogRows` + `buildMerchantProduct`) فلا تتباعد القناتان في السعر أو التوفّر.

## المسارات الأربعة

```
1) رفع أولي     enqueueFullCatalog   ← زر في لوحة التحكم، يصفّ الكتالوج كاملاً
2) لحظي         domain_events        ← product.updated · product.unpublished · inventory.changed
3) عامل الطابور  processMerchantQueue ← كل دقيقة، custombatch بحد ٥٠٠
4) مطابقة ليلية  reconcileMerchant    ← انحراف + انتهاء صلاحية + أسباب الرفض
```

المسارات ١ و٢ لا ترسلان شيئاً بنفسيهما: كلاهما يكتب في `merchant_sync_state` ويصرّفه المسار ٣،
فيرث الرفع الأولي نفس التراجع الأُسّي وسجل الأخطاء ولا يوجد كودان للإرسال.

## جدول الحالة
`merchant_sync_state` — صف لكل منتج:

| العمود | الدور |
| --- | --- |
| `google_id` | `online:ar:SA:<offer_id>` — مفتاح المنتج عند جوجل، لا يتغيّر بعد أول رفع |
| `offer_id` | الـ SKU لا الـ UUID: يظهر في تقارير جوجل ويقرأه بشر |
| `payload_hash` | إن لم تتغيّر البصمة لا يُرسل شيء — تعديل حقل داخلي لا يستهلك حصة |
| `last_synced_at` | يقود إعادة الرفع قبل انتهاء الصلاحية |
| `status` | `pending · pending_delete · synced · failed · disapproved · deleted` |
| `issues` | أسباب الرفض من `productstatuses` كما تُعرض للتاجر |

## انتهاء الصلاحية
منتجات Merchant Center **تنتهي بعد ٣٠ يوماً** من آخر رفع. المطابقة الليلية تعيد رفع كل ما مضى
عليه ٢٥ يوماً (هامش خمسة أيام يحتمل عدة دورات فاشلة). هذا وحده سبب كافٍ لوجودها حتى لو لم
يتغيّر شيء في الكتالوج.

## معالجة الأخطاء
- **429 و5xx و`internalError`/`rateLimitExceeded`** → عابر: تراجع أُسّي حتى خمس محاولات.
- **باقي أخطاء 4xx** (سعر مخالف، حقل ناقص) → لا يُصلحها التكرار: الصف يصبح `failed` فوراً
  ويظهر سببه في لوحة التحكم.
- **الدفعة تنجح جزئياً**: استجابة `custombatch` تُقرأ عنصراً عنصراً؛ معاملتها كوحدة تُسقط منتجات سليمة.

## ما يرفضه جوجل عادةً
- **السعر في الخلاصة ≠ السعر في الصفحة** — جوجل يزحف للصفحة ويقارن. المصدر واحد هنا
  (`product_variants.price`)، لكن انتبه للضريبة: صفحة تعرض سعراً شاملاً وخلاصة ترسل غير شامل = رفض فوري.
- **منتجات رقمية بلا سياسة إرجاع وشروط واضحة** — تُرفض تحت «معلومات غير كافية».
- **معرّف عالمي ناقص**: نرسل `identifierExists: false` صراحةً لأن منتجات المتجر بلا GTIN.

## الإعداد
1. حساب خدمة من Google Cloud + تفعيل Content API for Shopping.
2. إضافة بريد حساب الخدمة كمستخدم في Merchant Center.
3. في `/admin/settings/integrations` → **Google Merchant Center**: أدخل Merchant ID والصق ملف
   JSON كاملاً (يُخزَّن مشفّراً AES-256-GCM ولا يعود للواجهة إلا مقنّعاً)، ثم فعّل التكامل.
4. اضغط **رفع الكتالوج كاملاً** مرة واحدة.

## المجدولات
```
POST /api/internal/process-merchant     كل دقيقة   x-cron-secret: $CRON_SECRET
POST /api/internal/reconcile-merchant   يومياً ٣ فجراً
```

## الاختبار
```
npm run test:feeds   # بلا قاعدة بيانات: المعرّف المركّب، التسعير، التوفّر، البصمة، XML
```

## ملاحظة على الإصدار
العميل مبني على **Content API for Shopping v2.1**، وكل ما يخص إصدار واجهة جوجل محبوس في
`src/modules/feeds/infrastructure/content-api.ts`. جوجل تنقل المطوّرين تدريجياً إلى Merchant API
الأحدث؛ الانتقال يمسّ هذا الملف وحده ولا يمسّ منطق المزامنة.
